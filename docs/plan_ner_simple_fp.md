# План улучшения извлечения имён и метрик

## Коротко

Сейчас в проекте уже есть рабочий, но довольно жёсткий эвристический NER: он ищет слова с заглавной буквы, пытается нормализовать их через `pymorphy2` и затем считает частоты. Это хороший старт, но у него есть слабые места:

- много ложных срабатываний;
- пропуски имён в середине предложения;
- слабое объединение форм одного и того же имени;
- логика смешана: извлечение, фильтрация, нормализация и агрегация идут в одном месте;
- почти нет чистых функций, поэтому код труднее тестировать и менять.

Ниже — более простой и функциональный план. Его цель: не усложнять систему, а сделать её **составной, предсказуемой и проверяемой**.

---

## Что не так с прежним планом

### 1. Слишком много уровней сразу
В прежнем варианте одновременно предлагались:
- spaCy / Stanza / Natasha;
- coreference resolution;
- fuzzy clustering;
- embeddings;
- интерактивный review;
- scoring с несколькими весами.

Для проекта с простым текстовым пайплайном это слишком много. Такая схема:
- тяжело отлаживается;
- плохо переносится в Termux и на слабые устройства;
- создаёт сложные зависимости;
- делает поведение менее прозрачным.

### 2. Смешаны разные задачи
В одном плане были объединены:
- поиск кандидатов,
- проверка морфологии,
- объединение форм,
- оценка уверенности,
- экспорт,
- ручная модерация.

Лучше разделить это на независимые шаги. Тогда каждый шаг можно тестировать отдельно.

### 3. Много “умных” эвристик без необходимости
Весовые формулы вида `score = w1 * freq + w2 * morph + ...` выглядят гибко, но на практике:
- сложно понять, почему имя прошло или не прошло;
- трудно подобрать веса;
- поведение становится нестабильным.

В функциональном и простом подходе лучше использовать **явные правила** вместо “магических” скорингов, где это возможно.

### 4. Не хватает чистых функций
Хороший функциональный стиль — это когда:
- функция получает данные и возвращает данные;
- не меняет глобальное состояние;
- не зависит от скрытого окружения;
- легко тестируется.

В текущем плане много объектов и внутренних состояний. Это допустимо для загрузки моделей, но сама логика извлечения должна быть по возможности чистой.

---

## Улучшенный принцип

### Главная идея
Сделать NER как цепочку простых функций:

1. **normalize_text(text) -> text**
2. **tokenize(text) -> tokens**
3. **find_candidates(tokens) -> candidates**
4. **normalize_candidates(candidates) -> normalized_candidates**
5. **merge_candidates(normalized_candidates) -> entities**
6. **export_entities(entities) -> files**

Каждая функция делает только одно.

---

## Предлагаемый простой план

### Этап 1. Оставить один базовый метод
Сначала не подключать spaCy, Natasha и Stanza.

Использовать только:
- `pymorphy2` для нормализации;
- текущую токенизацию;
- простые правила для имён собственных.

Это даст понятный baseline и позволит улучшать качество постепенно.

### Этап 2. Разделить логику на чистые функции
Нужно выделить отдельные функции:

- `normalize_text(text)`
- `split_sentences(text)`
- `tokenize_sentence(sentence)`
- `is_name_candidate(token, prev_token, next_token)`
- `canonicalize_name(name)`
- `group_mentions(mentions)`

Тогда NER станет не монолитом, а набором маленьких трансформаций.

### Этап 3. Упростить правила отбора
Вместо сложного score использовать понятные фильтры:

- слово начинается с заглавной буквы;
- слово не стоит в списке стоп-слов;
- слово не является началом предложения без дополнительного контекста;
- для русского языка `pymorphy2` подтверждает, что слово похоже на имя, фамилию или отчество;
- составные имена собираются только из соседних подходящих токенов.

Если правило не ясно объясняется человеку, его лучше не добавлять.

### Этап 4. Объединение форм делать по нормальной форме
Для русских текстов основа объединения — лемма от `pymorphy2`.

Пример:
- Иван
- Ивана
- Ивану
- Иваном

Должны попадать в один кластер, если это действительно одно имя.

Для многословных имён объединение делать так:
- нормализовать каждое слово отдельно;
- объединять только соседние слова, если оба похожи на части имени.

### Этап 5. Добавить только минимальные метрики
Не надо сразу внедрять много тяжёлых метрик или моделей.

Для начала достаточно:
- частоты;
- число уникальных форм;
- число упоминаний по главам;
- доля имён среди всех токенов;
- простая связанность персонажей по совместной встречаемости.

Позже можно добавить более сложные метрики, если появится реальная потребность.

## Какой должен быть функциональный стиль

### Хорошие свойства

- функция не меняет входные данные;
- результат зависит только от входа;
- одинаковый вход даёт одинаковый выход;
- можно писать маленькие тесты.

### Пример правильного разбиения

Плохо:
- одна функция читает файл;
- нормализует текст;
- ищет имена;
- пишет CSV;
- считает статистику.

Хорошо:
- `read_text(path)`
- `normalize_text(text)`
- `extract_names(text, config)`
- `build_statistics(names)`
- `write_csv(records, path)`

## Практический состав модуля

### 1. `ner_heuristic.py`
Оставить в нём только простую эвристику:
- поиск заглавных последовательностей;
- проверка через стоп-слова;
- нормализация через `pymorphy2`;
- агрегация одинаковых форм.

### 2. `ner_model.py` — не обязательно на старте
Если потом понадобится spaCy или Stanza, лучше не смешивать их с эвристикой. Тогда `ner_model.py` должен быть отдельной обёрткой.

Но в духе простоты лучше сначала не делать этот модуль обязательным.

### 3. `metrics.py`
Добавлять только те метрики, которые реально используются в анализе текста.

### 4. `config.py`
Конфигурация должна быть короткой и понятной.

Лучше иметь такие параметры:
- `lang`
- `use_lemmas`
- `ner_mode`
- `min_name_length`
- `min_occurrences`
- `verbose`

Не стоит добавлять десятки флагов заранее.

## Какие алгоритмы поиска имён подходят в этом проекте

### Базовый уровень
1. **Capitalized sequence heuristic**
   - искать слова с заглавной буквы;
   - собирать соседние слова в составные имена.

2. **Morphological filtering with pymorphy2**
   - проверять, похоже ли слово на имя, фамилию или отчество;
   - приводить к нормальной форме.

3. **Blacklist + context rules**
   - отсекать частые ложные срабатывания;
   - учитывать начало предложения, диалог, обращения.

### Средний уровень
4. **POS-based filtering**
   - если появится POS-разметка, отбирать `PROPN`.

### Поздний уровень
5. **spaCy / Stanza / Natasha**
   - подключать только если эвристика уже недостаточна.

Для текущего проекта разумнее идти от простого к сложному.

---

## Какие метрики для литературных текстов стоит добавить

Сейчас есть частоты, hapax, Yule’s K, Honore’s R, лексическая плотность.

Ещё полезны:

- **TTR** — type-token ratio;
- **MATTR** — скользящий TTR;
- **MTLD** — более устойчивый показатель лексического богатства;
- **Guiraud’s R**;
- **Shannon entropy** для распределения слов;
- **Simpson index**;
- **средняя длина предложения**;
- **доля диалогов**;
- **число персонажей на 1000 слов**;
- **граф персонажей** по совместной встречаемости;
- **распределение частоты по главам**.

Но добавлять их нужно только после того, как станет понятно, зачем они нужны в анализе.

## Рекомендуемый минимальный план работ

### Шаг 1
Оставить один простой NER-путь на базе текущей эвристики и `pymorphy2`.

### Шаг 2
Разбить код на чистые функции.

### Шаг 3
Добавить маленькие тесты на:
- извлечение имён;
- нормализацию форм;
- объединение склонений;
- отсечение ложных срабатываний.

### Шаг 4
Добавить только одну-две новые метрики.

### Шаг 5
Только если качество всё ещё недостаточно, подключать внешний NER-бэкенд как отдельную опцию.

---

## Что не стоит делать сейчас

- не вводить тяжёлые модели по умолчанию;
- не строить сложную scoring-систему без размеченных данных;
- не смешивать эвристику, ML и ручную модерацию в одном проходе;
- не добавлять много параметров конфигурации заранее;
- не делать код зависимым от внешнего сервиса.

---

## Итог

Для этого проекта лучший путь такой:

- **простая эвристика** как база;
- **чистые функции** вместо большого объекта со скрытым состоянием;
- **`pymorphy2`** как главный инструмент нормализации;
- **маленькие тесты** вместо сложной логики без проверки;
- **добавлять сложность только по необходимости**.

Это соответствует и функциональному стилю, и принципу простоты.
